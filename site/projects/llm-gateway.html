LLM Gateway

An OpenAI-compatible gateway that routes across LLM providers with automatic failover, exposes agent tools over MCP, and evaluates answer quality in CI.

The problem

Single-provider applications inherit every provider outage.

Most AI features are coupled directly to one model provider. Outages, latency spikes and price changes reach every user, and switching providers requires code changes. Each team also rebuilds the same infrastructure: access control, rate limiting, cost tracking and agent tooling.

The gateway sits between applications and providers, accepts the request format applications already use, and handles routing, failover and policy centrally.

How it works

Every request takes the same path.

1. The app calls one endpointSame request format as OpenAI's API, so any existing SDK works unchanged.POST /v1/chat/completions
→
2. Security checkAPI key, per-key rate limit, personal data redacted from logs, audit trail. With no keys configured it refuses everything.
→
3. RouterTurns a request like "smart" or "cheap" into a ranked list of providers by order, cost or speed. Tries the first, falls back to the next on failure, and records the cost.
→
4. AnswerReturned in the same format, with which provider answered and what it cost.

What agents can use

MCP tool server · 11 toolsSearch maintenance manuals, read equipment data, and query live public data: UK river levels, aviation weather and ECB exchange rates.
A second agent (A2A)The main agent can hand a question to a specialist agent with its own prompt and model.
Evaluation in CIA golden set of questions checks tool use, grounding and answer quality, and fails the build on a regression.

Key decisions

Design decisions.

No agent framework

Every model call goes through my router, so fallback and cost tracking always apply. A framework would bring its own model clients and quietly skip both.

Trade-off: I'd revisit this only for multi-agent conversations or long-running workflow state.

Fail closed

If no API keys are configured, the service returns an error for every request instead of running open.

Trade-off: a misconfigured deployment fails safely instead of running unprotected.

Unknown cost is never shown as free

Only verified prices are recorded. Models without one report no cost and sort last when ranking by price.

Trade-off: some providers show "unknown" cost until their prices are verified.

Tools explain their own numbers

River levels are relative to a station marker, not water depth; exchange rates are daily reference rates. Those caveats live in the tool descriptions so the model can't misreport them.

Trade-off: longer tool descriptions, in exchange for fewer confident wrong answers.

Results

Verified results.

167automated tests, no network or keys needed
23 / 23evaluation cases passed against a live model and live data, for about $0.43
26 / 26end-to-end checks against a running server over real HTTP
  • The evaluation caught five real bugs that unit tests missed. For example, the AI judge failed a correct answer for "using a future date" because it guessed today's date from its training data. I fixed it by giving the judge the real date.
  • It also caught a factual error: the ECB publishes rates against the euro, so a pound-to-dollar rate is derived, and the tool now says so.
  • Live calls verified against Anthropic's API and all three public data sources.

Roadmap

Planned improvements.

  • Verify the OpenAI and Azure OpenAI adapters with real credentials. Today they're tested with mocks only.
  • Deploy to Azure. The infrastructure is written in Bicep but has not been applied.
  • Shared rate limits through Redis, so limits hold across several copies of the service.
  • A small web interface so non-engineers can try it without running Python.
