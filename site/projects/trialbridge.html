TrialBridge

Matches patients to clinical trials and evaluates every eligibility criterion, returning UNKNOWN rather than guessing when the record lacks the required data.

The problem

Patients miss trials, and trials miss patients.

Clinical trials test new treatments, and many struggle to enroll enough people. Meanwhile, patients who would qualify never hear about them. Matching is still done by hand: a research coordinator reads each trial's rules line by line against a patient's chart.

AI can accelerate screening, but in a clinical setting a confident wrong answer is dangerous. When a criterion depends on a measurement that was never recorded, the correct answer is UNKNOWN, not an estimate.

How it works

Search wide, then check every rule carefully.

1. Read the patient notePulls out age, sex, diagnosis, lab values and medications, and notices negations like "no prior insulin".
→
2. Search by meaningTurns the patient into a vector and finds the 50 closest of 2,344 trials stored in PostgreSQL with pgvector.
→
3. Rules and scoringChecks age range and required or excluded conditions, then ranks trials by similarity plus rule fit.
→
4. Eligibility agentClaude on Amazon Bedrock reads each criterion and asks for the facts it needs through a tool. Each criterion comes back MET, NOT MET or UNKNOWN, with evidence.

Key decisions

Making guessing impossible, not just discouraged.

The agent never sees the patient note

It has to request each fact through a tool. If the record doesn't contain a value, the tool literally answers "not present", so UNKNOWN is the only verdict left. The model can't fill the gap from a guess.

Trade-off: more tool calls per trial, in exchange for decisions you can audit.

Measure both kinds of mistake

The evaluation reports two rates together: confident decisions the record couldn't support, and UNKNOWN answers the record could have settled.

Trade-off: reporting only the first would be misleading, since a model that answers UNKNOWN to everything would score perfectly on it.

A smaller, faster search model

The plan was BioBERT. I shipped MiniLM instead: about 5 times faster at close to the same retrieval quality on this data.

Trade-off: the embedder is model-agnostic, so BioBERT can be swapped back in.

Let the model think before acting

With extended thinking turned off, the model sometimes wrote a tool call as plain text, which looks like a finished turn where nothing actually ran. Thinking stays on.

Trade-off: slightly slower and more tokens per decision.

Results

Verified results.

2,344trials ingested from the ClinicalTrials.gov bulk export
86automated tests, run in CI against live PostgreSQL
3possible verdicts per rule: met, not met, unknown
  • Full pipeline endpoint: paste a patient note and get ranked, scored trial matches back.
  • A data-quality pass over the raw export shaped the extraction rules before any matching code was written.
  • CI on every change: ruff lint and format, mypy type checks, and pytest with coverage.

Roadmap

Planned improvements.

  • Real sign-in. The login endpoint is a placeholder today.
  • Plain-English explanations for every match. The explainer is written but not yet connected to the match results.
  • A web interface for coordinators, and deployment to AWS.
  • Run the evaluation on more hand-labelled cases and publish both error rates.
