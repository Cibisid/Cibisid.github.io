Gauntlet

An evaluation-gated release platform for LLM and agent systems, with progressive canary rollouts and automatic rollback.

The problem

Model and prompt changes can silently degrade a product.

Teams revise prompts, switch to cheaper models and add guardrails continuously. Any of these changes can reduce accuracy, leak protected data, increase latency or raise costs, and regressions often surface only after customers notice, because few teams have a test suite for model behavior.

Gauntlet treats prompts, models and guardrails like code: every change is versioned, tested against the current version before it merges, and released gradually.

How it works

Two checkpoints: before release, and during it.

1. A change is proposedA pull request edits the release file: prompt, model, settings, guardrails or budgets.releases/*.yaml
→
2. Offline gateOld and new versions answer the same held-out cases. The new one must be statistically no worse, leak nothing to injection attacks, and stay inside error, speed and cost budgets.
→
3. Canary rolloutLive traffic shifts 1% → 10% → 50% → 100%. Each step widens only while errors, response time, leaks and quality scores stay healthy.
→
4. Promote or roll backHealthy: the new version takes all traffic. Not healthy: it switches back automatically and writes the reason to a tamper-evident audit log.

Around it

ProxyRoutes stable and canary traffic, hashes API keys, rate-limits, redacts personal data from traces.
MonitoringPrometheus metrics, a Grafana dashboard, 7 alerts with runbooks, and drift detection.
DeployHardened Docker image, Kubernetes manifests and Terraform for AWS, all scanned in CI.

Key decisions

The choices that make the gate trustworthy.

Use statistics, not a fixed score cutoff

A candidate passes only if we're confident it is no more than 3 points worse than the current version, using paired bootstrap non-inferiority testing.

Trade-off: 192 test cases were too few to prove even a harmless change was safe. I grew the suite to 474 instead of loosening the margin.

AI judges must earn the right to block a release

An LLM judge can gate only after it agrees with human labels: Cohen's kappa of at least 0.6 and catching at least 80% of real failures, across at least 200 labelled examples.

Trade-off: until those labels exist, the judge only reports. Simulated labels don't count.

Block leaks at the output, not the input

My pattern-based injection detector caught 40 of 40 known attacks but 0 of 20 new ones. So enforcement moved to the output side: block protected strings and redact personal data before anything leaves.

Trade-off: the input detector stays, but only as a monitored signal.

A free, repeatable test model in CI

CI runs against a deterministic mock model so every check is free and gives the same answer twice. Real models run in a separate workflow.

Trade-off: CI proves the system's behaviour, not any model's quality. That's stated plainly in the README.

Results

Measured results.

≤ 1 msproxy overhead on 99.7% of 6,720 requests
250/speak requests per second on a shared 2-vCPU machine
137automated tests passing, about 98% coverage
  • The gate returned the correct verdict on all four demonstration releases: a harmless rewording passed, a cheaper model failed, a model without an output guardrail failed with 40 of 40 leaks, and the same model with the guardrail passed with 0 of 40.
  • Real models, real decision: on 514 cases, the smaller gpt-oss-20b scored 95.6% against 99.6% for gpt-oss-120b while costing about 55% less. The gate still said FAIL, because the drop could be as large as 3.9 points, past the 3-point limit.
  • Security in CI: OWASP ZAP, Bandit, Semgrep, gitleaks, pip-audit, Trivy and checkov run on every change, plus an end-to-end canary test on a local Kubernetes cluster.

Roadmap

Planned improvements.

  • Qualify the judge with 200 real human labels using the built-in labelling tool.
  • Run on real TrialBridge patient cases instead of the synthetic task.
  • Apply the AWS Terraform. It's written and scanned, about $38 a month to run.
  • High availability: share routing state so the proxy can run as more than one copy.
